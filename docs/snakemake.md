# Snakemake Workflow: Multi-Hypothesis Matrix

The CellQuorum Snakemake workflow orchestrates multi-hypothesis analyses in a reproducible pipeline. Each hypothesis runs against one or more cell types, generating per-cell-type analyses that are bundled into a unified hypothesis report. This document describes the manifest format, how to add hypotheses, and how to run and interpret the workflow.

## Manifest Format

The manifest (`workflow/hypotheses.yaml`) defines the set of hypotheses to run. Each entry is keyed by a hypothesis ID and contains:

### Required Fields

- **`title`**: Human-readable hypothesis title (used in reports).
- **`cell_types`**: List of cell types to analyze under this hypothesis (e.g., `[KC, ILC]`).
- **`inputs`**: Dictionary mapping each cell type to its input H5AD path. Use `TODO_SET_PATH` as a placeholder when the path is not yet configured.

### Optional Fields

- **`skip`**: Dictionary mapping stage names to reason strings. Stages listed here are skipped in config generation. Example:
  ```yaml
  skip:
    rna_velocity: "velocity not applicable for this cell type"
  ```

- **`blocked`**: Dictionary mapping stage names to reason strings. Stages listed here are marked as blocked (cannot run) in config generation. Example:
  ```yaml
  blocked:
    rna_velocity: "spliced/unspliced not yet generated for these subsets"
  ```

- **`gene_programs`**: List of gene sets to score (for enrichment stages). Example:
  ```yaml
  gene_programs:
    - name: "EMT_signature"
      genes: [VIM, SNAI1, TWIST1, ZEB1]
  ```

- **`config_overrides`**: Dictionary of config overrides applied to the generated configs for this hypothesis. Use dot-notation keys to override nested fields. Example:
  ```yaml
  config_overrides:
    "qc.min_genes": 500
    "de.method": "wilcoxon"
  ```

### Example Manifest Entry

```yaml
emt_krt_high:
  title: "EMT / KRT-high keratinocyte program"
  cell_types: [KC]
  inputs: {KC: /data/lymphedema/kc_subset.h5ad}
  skip:
    trajectory: "EMT is a snapshot state; trajectory not needed"
  gene_programs:
    - name: "EMT_core"
      genes: [VIM, SNAI1, TWIST1, ZEB1, CDH2]
```

## Adding a Hypothesis

1. Open `workflow/hypotheses.yaml`.
2. Add a new top-level entry with a unique hypothesis ID (use snake_case).
3. Specify `title`, `cell_types`, and `inputs` (use `TODO_SET_PATH` for paths not yet configured).
4. Optionally add `skip`, `blocked`, `gene_programs`, or `config_overrides` as needed.
5. Run `make matrix` to validate the manifest and generate configs.

## Running the Workflow

### Generate Configs

Configs are auto-generated by the workflow, but you can inspect them:

```bash
snakemake --snakefile workflow/Snakefile gen_configs --cores 1
```

This reads the manifest and template, generates one config per `(hypothesis, cell_type)` pair, and writes them to `generated/configs/`.

### Run Full Matrix

Run all hypotheses:

```bash
make matrix
```

Or equivalently:

```bash
snakemake --snakefile workflow/Snakefile --cores 4 --keep-going
```

The `--keep-going` flag ensures that if one hypothesis fails, others continue to completion.

### Run Specific Hypothesis

Run a single hypothesis:

```bash
snakemake --snakefile workflow/Snakefile bundles/emt_krt_high/report.html --cores 4
```

## Workflow Stages

The workflow consists of five rules:

1. **`gen_configs`**: Generates per-`(hypothesis, cell_type)` configs from the manifest and template.
2. **`run_analysis`**: Runs `cellquorum run` for each `(hypothesis, cell_type)` pair, producing per-cell-type artifacts in `runs/<hypothesis>/<cell_type>/`.
3. **`bundle_hypothesis`**: Bundles all cell-type runs for a hypothesis into a unified report in `bundles/<hypothesis>/report.html`.
4. **`aggregate_status`**: Collects stage execution records across all runs and writes `runs/matrix_status.csv` and `runs/matrix_status.md`.
5. **`all`**: The default target, which builds all hypothesis reports plus the status matrix.

## Interpreting the Status Matrix

After running `make matrix`, inspect the status matrix:

```bash
cat runs/matrix_status.md
```

The matrix shows which stages completed, failed, or were skipped for each `(hypothesis, cell_type)` pair. Key columns:

- **`run_id`**: `<hypothesis>__<cell_type>` identifier.
- **Stage columns**: One column per stage, with values:
  - `ok`: Stage completed successfully.
  - `failed`: Stage failed.
  - `skipped`: Stage was skipped (either in manifest `skip` or via planner).
  - `blocked`: Stage was marked as blocked in manifest.
  - *(empty)*: Stage not yet run.

Use this to identify failures and bottlenecks across the hypothesis matrix.

## Configuration Details

### Template

The workflow uses `workflow/template.yaml` as the base config. This template is merged with hypothesis-specific overrides from the manifest to produce the final per-`(hypothesis, cell_type)` configs.

### Output Structure

```
generated/
  configs/
    <hypothesis>__<cell_type>.yaml   # Generated configs
  accounting.json                    # Completeness accounting
runs/
  <hypothesis>/
    <cell_type>/
      artifacts/                     # Stage outputs
      figures/                       # Generated figures
      provenance/                    # Execution records
        artifact_manifest.csv
        stage_execution_records.json
  matrix_status.csv                  # Aggregated status (CSV)
  matrix_status.md                   # Aggregated status (Markdown)
bundles/
  <hypothesis>/
    report.html                      # Unified hypothesis report
    artifacts/                       # Bundled artifacts
```

## Notes

- **Idempotency**: Re-running the workflow skips completed stages (Snakemake detects existing outputs).
- **Parallel execution**: Increase `--cores` to run multiple hypotheses in parallel.
- **Docker integration**: Use `make matrix` to run the workflow inside the Docker image (see `docs/docker.md`).
- **Environment isolation**: The workflow automatically invokes isolated backend environments (pyscenic_env, scclr, etc.) as needed via `micromamba run -n <env>`.
